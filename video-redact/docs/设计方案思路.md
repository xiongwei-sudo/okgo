## 1. 我们要解决什么

目标很具体：做一个**网页可用的本地视频脱敏工具**，把演示／样片里的隐私目标打掉，并可选走一条**视频增强**支线。

| 能力 | 一期要覆盖的 |
|------|----------------|
| 打码 | 人脸、车牌、敏感文字（身份证号／手机号等，OCR + 正则） |
| 增强 | 超分／去噪／低光／稳像等（N1–N4），与打码共用队列与网页壳 |
| 场景 | 公安**视综**业务演示、样片脱敏、内网隐私保护——素材不出公网大模型 |

刻意压住的范围（一期不做）：实时摄像头流、云端大模型 OCR、精确字符级擦除、跨镜头再识别、音频脱敏、插帧大模型、生成式全片修复。

一句话：**单机可跑、可演示、可交付样片；先把链路跑通，再换专用权重。**

## 2. 已经钉死的工程约定

这些是对话里反复确认、写进 README／方案的「锁死项」，后续实现不要轻易翻案：

| 决策 | 为什么这样定 |
|------|----------------|
| **不做容器** | 云机（AutoDL／Seetacloud）本身就是整机环境；一期要快落地，venv／conda 足够，少一层镜像心智负担。 |
| **进程级任务队列** | FastAPI 只接上传／进度／下载；真正占 GPU 的工作进 Worker。一期用**内存队列**，每卡 concurrency=1；二期再考虑 Redis + RQ／Arq。 |
| **模型按需加载** | 人脸／车牌／OCR／增强模型种类多，常驻会挤满显存；按 job 勾选加载，任务结束可卸载，热点模型可用 LRU 常驻。 |
| **一卡一任务** | 禁止多路视频任务抢同一张卡；增强与打码共用 Worker 池、互斥占卡。多卡时是「一卡一 worker」，不做单任务切卡。 |
| **默认先增强、后打码** | 先超分／去噪再打马赛克，避免把马赛克块一起放大。CLI `--enhance`、网页增强开关按此编排；也可拆成独立 enhance／redact job。 |
| **OCR 保留** | 敏感文字是一期三类目标之一；用 RapidOCR（检测 + 识别）+ 身份证／手机号正则过滤，避免把所有字幕／招牌一律打掉。 |
| **网页用 FastAPI** | 单页中文 HTML/JS + 标准 REST（上传／轮询／下载）；云机常用端口 **6006**。CLI 与网页共用同一套 `pipeline/`。 |

补充约定：打码与跟踪后处理放 **CPU**；推理默认 GPU FP16，CPU 可回退；结果视频用 ffmpeg 从原片**回嵌音轨**。

## 3. 模型与算法选型（一期）

选型原则：**能公开装、能开关、接口可替换**；缺专用权重时必须有降级路径，保证流水线可冒烟。

### 3.1 检测与打码

| 模块 | 主力 | 降级／备选 | 备注 |
|------|------|------------|------|
| 人脸 | MediaPipe Face Detection 或 **YuNet** | OpenCV DNN | CPU 友好；YuNet onnx 可由脚本拉取 |
| 车牌 | **YOLOv8n** 车牌微调 `.pt` | 颜色＋轮廓启发式 | 公开中国车牌权重【待补】；失败写 `PLATE_WEIGHTS_PENDING` |
| 文字 | **RapidOCR**（PP-OCRv4 det+rec ONNX） | — | 识别结果只服务敏感正则，不追求全文 OCR |
| 模糊 | 高斯（默认）／马赛克／可选纯色 | — | 人脸偏高斯，车牌／证件号偏马赛克 |
| 跟踪 | 简易 IoU；可升 **ByteTrack** 轻量 | — | 短时漏检外推，减轻闪烁；框外扩约 10%～15% |

### 3.2 增强（N1–N4）

| 阶段 | 能力 | 主力模型 | 无权重时 |
|------|------|----------|----------|
| N1 | 超分 | Real-ESRGAN x2／x4 | OpenCV 同分辨率增强／锐化等 |
| N2 | 去噪／低光 | NAFNet／Restormer；Zero-DCE++／SCI | CLAHE、非局部均值去噪等 |
| N3 | 稳像 | OpenCV／vidstab | 几何补偿路径本身偏轻量 |
| N4 | 视频超分（二期） | BasicVSR++ | 未做 |

增强内部建议顺序：**稳像 → 低光 → 去噪／去糊 → 超分**，避免先放大噪声。专用权重【待补】时，`pipeline/enhance.py` 的 OpenCV 降级保证开关与编排可跑通。

## 4. 硬件与运行环境

对话与探测落地的环境画像：

| 项 | 取值 |
|----|------|
| 云厂商 | AutoDL／Seetacloud |
| GPU | **RTX 5090 D**，约 **32GB** 显存 |
| CUDA | 主机常见 **12.8**；驱动版本可能报更高，以 `nvidia-smi` 为准 |
| 磁盘 | 系统盘紧（约数十 GB）；工程／权重／视频放数据盘 `/root/autodl-tmp/video-redact` |
| 代码位置 | GitHub [`okgo`](https://github.com/xiongwei-sudo/okgo) 仓库下的 **`video-redact/`** 子目录（保留博客，不覆盖主站） |

### 预装 PyTorch vs 项目 venv（取舍）

云镜像通常**已预装**系统级 PyTorch。推进时曾为隔离在 `.venv` 内再装一套 **cu128**，体积大、下载慢（torch wheel + CUDA 依赖数 GB）。

| 路线 | 优点 | 代价 |
|------|------|------|
| 直接用预装 torch | 省时间、省磁盘 | 版本与镜像绑定，换机要再验 |
| 项目 `.venv` + cu128 | 与文档／CUDA 12.8 对齐、依赖可复现 | 首次安装很重 |

当前实践：云机侧继续把隔离环境装完以便冒烟；**部署说明同时写明「可优先复用预装 torch，只补缺包」**，按磁盘与时间二选一。不要在系统盘堆权重和视频。

## 5. GPU 调度思路

32G 看起来宽裕，但「打码三模型 + 增强大模型」叠在一起仍会顶满。约定如下：

1. **任务级串行** — 每卡同一时刻只跑一个视频 job（redact 或 enhance）。  
2. **帧内模型串行** — 一批帧上按勾选：人脸 → 车牌 YOLO → OCR；同一时刻一张卡只做一个 forward。  
3. **批帧与 stride** — 默认 batch 约 4～8（按显存下调）；可选检测步长 2／3，中间帧靠跟踪补框。  
4. **显存预留** — 工作集建议压在约 28GB 内，留约 1～2GB+ 给驱动／碎片；OOM 时降 batch → 降检测分辨率／tile → 降超分倍率。  
5. **不做** — 多模型 CUDA 流硬并行抢同卡；单帧三模型拆到三卡。

背压：FIFO + 时长／体积限额；队列满返回忙；每 job 记排队与各段耗时。

## 6. 分期与仓库形态

### 打码主线 M1–M5

| 里程碑 | 含义 | 推进共识 |
|--------|------|----------|
| M1 | CLI／网页：上传→人脸模糊→下载 | 骨架已齐 |
| M2 | 车牌 + 马赛克 + ffmpeg 音轨 | 逻辑有；专用权重【待补】时启发式 |
| M3 | OCR 敏感过滤 + 简易跟踪 | RapidOCR 路径已接 |
| M4 | GPU Worker：按需加载、批帧、stride、队列背压 | 进行中（内存队列 concurrency=1） |
| M5 | 多卡一卡一 worker + 配置面板 | 未做 |

### 增强支线 N1–N4

N1 超分 → N2 诊断＋低光／去噪 → N3 稳像与打码 pipeline → N4 BasicVSR++。当前以 **OpenCV 降级** 打通编排，专用权重到位后再切主力模型。

### Git 与制品

| 项 | 约定 |
|----|------|
| 仓库 | 放在 `okgo/video-redact/`，经 PR（如 okgo#1）合入，**不冲掉**博客主站 |
| 权重 | `.pt`／`.onnx` 走 **Git LFS**（`.gitattributes` 已配）；下载脚本多源尝试 |
| 文档 | `docs/技术方案.md`、`docs/GPU部署安装说明.md`、本文；索引见 `docs/README.md` |
| 部署文档 | 已存在：SSH、数据盘、预装 torch／venv、拉人脸与增强权重、CLI／网页:6006、冒烟 |

并行策略也成立过共识：**云机装依赖** 与 **本地／PR 补代码与文档** 可以同时推进，互不阻塞。

## 7. 仍未关闭的事项

| 开放项 | 说明 |
|--------|------|
| 车牌专用权重 | 公开微调 `.pt` 多源拉取仍可能失败；需落盘真实权重或明确长期启发式策略 |
| 增强官方权重 | Real-ESRGAN／NAFNet／Zero-DCE++ 等尚未全部进 `weights/enhance/`；缺则 OpenCV 降级 |
| PR 合并 | 源码与文档在 PR 侧；主分支需用户合并后才「仓库即真相」 |
| 云机冒烟 | 依赖装完后跑 `scripts/download_weights.py` + `scripts/smoke_test.sh`，用合成样片验收 |
| M4／M5／N4 | 队列与多卡、BasicVSR++ 等仍按分期往后排 |

合规提醒（与技术方案一致）：工具用于**合法授权素材**的隐私保护与演示脱敏；检测无法保证 100% 覆盖，重要交付仍需人工抽检。
